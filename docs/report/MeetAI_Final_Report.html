1. Abstract

MeetAI is a local-first AI meeting and productivity assistant for a normal student laptop. It schedules and joins Google Meet meetings through Playwright with a persistent browser profile, records the screen and audio with FFmpeg, transcribes the recording with faster-whisper, and analyses the transcript with a local Llama 3 model served by Ollama. The analysis produces structured meeting intelligence: a summary, key points, decisions, action items with owners and deadlines, open questions and follow-ups. The system then creates tasks, indexes everything for retrieval-augmented question answering with the embeddinggemma embedding model, and optionally emails the summary or publishes it to Notion.

This report documents an engineering audit and repair of the existing project. A complete inspection found 42 issues, including a committed API token, a model default that Google has shut down, missing AI fallback, missing RAG, network exposure of an authentication-free API, and several Windows-specific crashes. 40 of them were fixed and verified. The work added an AI Service Manager (Ollama → Gemini key 1 → Gemini key 2), a RAG subsystem (ChromaDB or MongoDB vectors), an email service, per-stage activity tracking and centralised error handling. The automated test suite grew from 62 to 122 tests, and a live end-to-end run on real local models passed 23 of 23 steps. Every core component is free and runs offline. Cloud services are optional fallbacks.

2. Problem Statement

Students and small teams spend many hours in online meetings, but decisions and action items are rarely captured in a searchable form. Existing meeting assistants are mostly paid cloud services that upload private audio to third-party servers, need subscriptions, and cannot answer questions across a personal meeting archive. A student with little or no budget needs a tool that:

  • joins and records meetings automatically without handing over account passwords;
  • transcribes and summarises locally, so private conversations never leave the computer by default;
  • extracts decisions, owners and deadlines reliably, even from small local models that produce imperfect JSON;
  • keeps working when one component (AI provider, email, Notion) is unavailable;
  • lets the user ask natural-language questions about all previous meetings;
  • installs and runs on Windows with free software only.

4. Existing System

The inspected repository (commit 852a61a plus uncommitted work) already had a solid base. It had a React 18 + TypeScript + Vite dashboard, an Express 4 API with MongoDB/Mongoose, a Playwright Google Meet bot, an FFmpeg recorder, local Whisper transcription, an Ollama analysis step with Joi-validated JSON, optional Gmail and Notion integrations, and 62 passing tests. Type-checking, linting and the production build were all clean.

The inspection found the following limitations:

  • AI: a single provider chosen in configuration, with no fallback, no Gemini key rotation and no error classification. The configured Gemini model (gemini-2.0-flash) has been shut down by Google. Ollama was called without num_ctx, so long transcripts were silently truncated.
  • No RAG: no embeddings, no vector store and no search over past meetings.
  • No email notifications beyond a minimal welcome mail. There was no activity timeline and no per-stage status.
  • Security: a real Notion token in .env.example, self-registration as ADMIN, reflected XSS in the OAuth callback, regex injection in search, and an authentication-free API reachable from the local network.
  • Windows: a copied .env pointing FFmpeg to another user's folder, a device list that FFmpeg 9 never populated, and a Vite watcher that crashed while a recording was being written.

7. System Architecture

MeetAI is a classic three-tier local application. A single-page React dashboard talks only to the local Express API through Vite's dev proxy, or from the same origin in production. The API delegates every capability to a service layer, and the services drive local tools (Chrome, FFmpeg, Python Whisper, Ollama, MongoDB, the file system) and optional internet services.

9. Frontend Architecture

The dashboard (src/) is a React Router SPA. AppLayout provides the sidebar and top bar. Pages are Dashboard, Meetings, Meeting details (Overview, Activity, Recording, Transcript, AI summary, Action items, Decisions, Notion), Tasks, Recordings, Ask meetings (new), Analytics and Settings. All data access goes through services/api/meetaiApi.ts and TanStack Query hooks in services/queries.ts. Busy meetings poll every 4 seconds, and the dashboard activity feed refreshes every 15 seconds.

  • API client (client.ts): reads the new error envelope (error.code, error.message). With AUTH_ENABLED=true, a 401 triggers one shared /auth/refresh call and the original request is retried. A failed refresh logs the user out cleanly.
  • No secrets in the bundle: there are no VITE_* secrets. Gemini, SMTP and Notion keys never reach the browser, and the settings endpoint only returns presence flags such as geminiKeyCount.
  • Bundle: vendor libraries are split into chunks (react, charts, data, motion). The largest chunk dropped from 1.3 MB to 424 kB.
  • New components: Activity.tsx (stage grid and timeline), KnowledgePage.tsx (RAG ask, search and document upload), the system status strip on the dashboard, and the email and provider controls in Settings.

12. AI Architecture

All model access goes through one class, AIServiceManager. Controllers never call a provider directly, so AI logic exists in one place only. Callers ask for a completion (generate) or embeddings (embed). The manager picks the provider chain, retries and falls back, and reports which provider answered together with every attempt.

Meeting analysis. analyzeTranscript() builds a strict JSON prompt. If the transcript is longer than AI_ANALYSIS_CHUNK_CHARS (12,000), it first condenses each part to factual notes (map) and then analyses the combined notes (reduce). The reply is extracted (code fences and prose are tolerated), validated with Joi and normalised: placeholder words such as "N/A" are removed, unknown enum values become MEDIUM or NEUTRAL, and an empty short summary is derived from the summary. If no valid JSON can be extracted, one correction prompt is sent. If that also fails, the stage is marked FAILED and the recording and transcript are kept for a retry.

13. Ollama Architecture

  • Endpoints: /api/generate for completions (format:"json", temperature 0.2, num_ctx = OLLAMA_NUM_CTX, default 8192), /api/embed for batched embeddings, and /api/tags for health (whether the chat and embedding models are pulled).
  • Models come from configuration, never assumed: OLLAMA_CHAT_MODEL=llama3 and OLLAMA_EMBEDDING_MODEL=embeddinggemma. Other installed models such as codeAI and grammerAI (both llama3-based) can be selected in Settings.
  • Errors: connection refused → UNAVAILABLE (15-second cooldown), abort → TIMEOUT (retried), 404 → MODEL_NOT_FOUND with an ollama pull hint.
  • Measured on this laptop (RTX 2050, 4 GB VRAM): a small JSON reply in about 12.6 s cold, 2 embeddings in 2.2 s, a full meeting analysis in 37 s, and a RAG answer in 5.7–12.8 s.

Keys are read only from .env, sent only in the x-goog-api-key header (never in a URL), and never included in error messages. Log lines are also scrubbed of key-shaped strings (AIza…, ntn_…, bearer tokens, JWTs). Privacy controls: AI_PROVIDER=ollama never contacts Gemini, AI_CLOUD_FALLBACK=false disables the automatic fallback, and RAG answers use cloud models only when RAG_ALLOW_CLOUD=true.

Free-tier note: Google publishes per-project limits in AI Studio rather than as fixed numbers, and may use free-tier prompts to improve its products. This is why Gemini is a fallback, not the default.

15. RAG Architecture

  • Sources: AI notes (dense summary, decisions, owners and deadlines), meeting description and notes, the raw transcript, and user documents (document, note, preference, profile; pasted or loaded from .txt/.md in the browser, so there is no binary upload endpoint).
  • Chunking: 1,200 characters with 200 overlap, cut at paragraph, sentence or word boundaries. The overlap snaps to the next word (a live test found and fixed mid-word starts).
  • Store selection: ChromaDB when CHROMA_URL is set and its heartbeat answers; otherwise MongoDB (RagChunk) with cosine similarity computed in Node. The choice is re-checked every minute, and falling back is logged.
  • Isolation: every chunk carries owner; retrieval filters by owner, and optionally by meeting. Deleting a meeting removes its vectors.
  • Answering: top-5 passages are numbered and the model must answer only from them with [n] citations. Re-indexing everything after switching stores is one click.

16. Meeting Automation Architecture

The scheduler checks every 30 seconds for UPCOMING meetings with autoJoin that start within the join offset (and started less than 15 minutes ago). The Playwright bot launches a persistent context on browser-profile/, trying Chrome, then Edge, then bundled Chromium. It fills the display name, turns the microphone and camera off, and clicks the join action. Join detection is anchored so that buttons such as "Other ways to join" are never clicked. A monitor polls every 20 seconds for the end of the call (left / removed / no Leave button) and stops the recorder automatically. The bot never handles a Google password: the user signs in once in the profile window.

17. Recording Pipeline

Before recording, the recorder checks that FFmpeg is available and that the configured DirectShow audio device exists. FFmpeg 9 exits with code 0 when listing devices, which the original parser did not handle. It refuses to make a silent recording unless RECORDER_ALLOW_VIDEO_ONLY=true, and stops gracefully by sending q so the MP4 container is finalised. Distinct, actionable errors are reported for: FFmpeg missing, wrong path, unknown device, empty or missing output file, and recording disabled.

18. Transcription Pipeline

The pipeline extracts 16 kHz mono PCM audio from the MP4, auto-detects the installed engine, and runs it with Hugging Face symlinks disabled (this avoids Windows error 1314 without administrator rights). CUDA failures fall back to the CPU. Progress updates are throttled to one database write every 3 seconds. The transcript is saved as transcripts/<meetingId>/transcript.txt and linked to the meeting. The WAV intermediate is removed and the MP4 is kept. A failure records the error on the meeting and never deletes the recording.

19. Email Architecture

EmailService (mailService.js) exposes sendMeetingSummary, sendTranscript, sendActionItems, sendNotification and sendDailyDigest. All user content is HTML-escaped. Sends never throw: the result is SENT, FAILED (with the SMTP error) or SKIPPED, and every attempt is written to EmailLog. The recommended free option is Gmail SMTP with an App Password (about 500 messages per day). Credentials are read only from .env, and connection timeouts are bounded.

21. Data Flow

HTTP handlers never wait for Whisper or the LLM. POST /process returns 202 with a durable ProcessingJob. One job runs at a time, because Whisper and Ollama each want the whole CPU. Each stage writes its state into meeting.stages and an ActivityLog row, which the UI polls.

23. Database Schema

Indexes include {owner, startTime, status, isDeleted} and a text index on Meeting; {owner, status, deadline, isDeleted} on Task; {meeting, createdAt} and {owner, createdAt} on ActivityLog; {owner, sourceId} on RagChunk; {meeting, createdAt} on ProcessingJob; and a unique email index on User.

28. Testing Strategy

  • Unit tests for pure logic: AI JSON extraction and normalisation, Gemini error classification, the chunker, cosine similarity, the Gmail parser, recorder arguments, dshow parsing and join-label detection.
  • Mocked-HTTP tests for the Ollama and Gemini providers (fetch stubbed): headers, num_ctx, 429 quota with retry hint, network failure, no key leakage.
  • Integration tests against a real local MongoDB using throwaway databases (meetai_test*): API CRUD, auth mode, authorization, security, RAG over the MongoDB vector store, and the full pipeline with a mocked LLM and a JSON email transport.
  • Live integration: a ChromaDB v2 server test (runs when Chroma is reachable), and the real Gemini API called with deliberately invalid keys to verify classification and blacklisting.
  • End-to-end against the running application with real local components: synthetic speech (Windows TTS) → MP4 → FFmpeg → faster-whisper → llama3 → tasks → RAG → Q&A → email → dashboard. Separately, a live Playwright join and FFmpeg recording against a local Google Meet mock page.
  • Static checks: tsc --noEmit, ESLint (0 warnings), vite build, npm audit, and a clean npm ci.

32. Error Handling

  • Central handler maps CastError → 400 INVALID_ID, ValidationError → 422, duplicate key → 409, JSON parse → 400 INVALID_JSON, oversized body → 413, JWT errors → 401. Unknown errors become 500 "Internal server error": the stack goes to logs/error.log and never into the response.
  • Pipeline: each stage is isolated. Transient failures (timeout, unavailable, 5xx, AI_PROVIDER_UNAVAILABLE) get one RETRYING attempt. Optional stages (RAG, Notion, email) can never fail a meeting. Analysis failure keeps the recording and transcript, still indexes the transcript, and can be retried.
  • Integrations report "not configured" instead of erroring. The status board wraps each check, so one broken service cannot hide the others.
  • Frontend shows error.message from the envelope; network errors explain that the API is not running.

34. Performance Considerations

  • One background job at a time: Whisper and llama3 each saturate the CPU, so parallel jobs would only slow both down.
  • Measured on the development laptop: 88 s of audio transcribed in 19 s; full analysis in 37 s; RAG answers in 6–13 s; embeddings for two chunks in 2.2 s.
  • Long meetings: map-reduce analysis keeps each prompt within num_ctx, so a 2-hour transcript is not truncated.
  • MongoDB vector search computes cosine similarity in Node over the owner's chunks. This is fine for thousands of chunks; ChromaDB (HNSW index) is recommended for larger archives.
  • Whisper progress writes are throttled to one every 3 s; recordings stream with HTTP Range; frontend vendor chunks are cached separately.
  • Low-RAM laptops can use llama3.2:3b, WHISPER_MODEL=tiny, OLLAMA_NUM_CTX=4096, or AI_PROVIDER=gemini.

35. Privacy Considerations

  • Default path is 100% local: audio, transcripts, notes, embeddings and answers never leave the computer.
  • Cloud use is explicit and limited: Gemini only as a fallback (can be disabled), RAG context only with RAG_ALLOW_CLOUD=true, email only to configured recipients.
  • APIs bind to localhost; no Google password is ever handled; the OAuth token is stored in a git-ignored .secrets/ folder with 0600 permissions.
  • Meetings, vectors and documents are owner-scoped; deleting a meeting removes its vectors.
  • Recording other participants may require their consent under local law. The user is responsible for informing participants.
  • During testing, the live screen and microphone capture was deleted immediately after verification, and screenshots in this report have local paths redacted.

37. Limitations

  • Real Google Meet joining was verified only against a local mock page. Google may change Meet's UI, and joining requires a signed-in profile and, for external meetings, host admission.
  • Windows has no built-in system-audio loopback. Capturing the other participants needs Stereo Mix or VB-Audio Virtual Cable; a microphone captures only the room.
  • Small local models under-extract occasionally. Prompting and validation reduce this but do not eliminate it. There is no speaker diarisation, so owners rely on spoken names.
  • Gemini success, SMTP delivery, Notion and Gmail were not exercised end-to-end, because no credentials were available.
  • The job queue is in-process: queued (not running) jobs are lost if the server restarts, although their records remain visible.
  • The daily digest function exists but has no scheduled trigger yet.
  • The token committed in local commit 852a61a remains in git history until the owner rewrites it.

39. Conclusion

The audit found that MeetAI's foundation was sound but not ready for real use. Its cloud fallback pointed to a retired model, it had a committed secret, an exposed authentication-free API, missing RAG and email, and several Windows failures that only appeared during real runs. After systematic fixes and additions, the application meets its local-first goal. A spoken meeting is recorded or imported, transcribed, analysed and turned into tasks, then made searchable and answerable, entirely with free local software and in about one minute for a 90-second meeting on a student laptop. The work was verified by 121 passing automated tests and live end-to-end runs. Every remaining gap is listed with the exact manual step required.
