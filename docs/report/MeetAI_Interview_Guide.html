1. The Project in One Minute

MeetAI is a free, local-first AI meeting assistant. You add a Google Meet link and a time. MeetAI joins the meeting by itself, records it, transcribes it on your own laptop, uses a local LLM to write the summary, decisions and action items, makes every meeting searchable by meaning (RAG), and emails you the summary. Everything runs on your machine; the cloud (Gemini) is only a backup.

How to say it: “I built a meeting assistant that runs entirely on a laptop. It joins Google Meet with Playwright, records with FFmpeg, transcribes with Whisper, and analyses with a local Llama 3 model through Ollama. It also has retrieval-augmented search across all past meetings and falls back to Gemini only if the local model fails.”

3. System Architecture

MeetAI is a three-tier application that runs on one computer:

  1. Presentation tier: React + TypeScript single-page app (Vite dev server on 127.0.0.1:5173). It only talks to the backend through /api/v1.
  2. Application tier: Node.js + Express REST API (127.0.0.1:5000), organised as routes → middleware → controllers → services → models. Each capability is a service: Meeting bot, Recorder, Transcription, AI Service Manager, RAG, Email, Notion.
  3. Data tier: MongoDB for structured data (meetings, tasks, activity, vectors) + the local disk for large files (MP4 recordings, transcripts, Markdown notes).

The services drive local tools: Chrome (via Playwright), FFmpeg, Python faster-whisper, and Ollama (Llama 3 + embeddinggemma). Internet services (Google Meet, Gemini, Gmail SMTP, Notion) are used only where unavoidable or optional.

How to say it: “It’s a layered monolith: a thin controller layer and a service layer that wraps each external tool, so I can swap Whisper implementations or AI providers without touching the API.”

5. End-to-End Workflow (Step by Step)

  1. Add a meeting — title, Meet link and start time (manual form; Gmail invitation detection is optional).
  2. Scheduler — every 30 s it looks for meetings starting within 2 minutes.
  3. Join — Playwright opens Chrome with the saved profile, waits for Meet’s join screen, clears pop-ups, types the name, keeps mic/camera off and clicks Join now / Ask to join (details in section 6).
  4. Record — once inside the call, an FFmpeg process captures the screen and the audio device into recordings/<id>/meeting-<time>.mp4.
  5. Detect the end — every 20 s the bot checks whether the call is still running; when it ends (or you press Stop) FFmpeg finalises the MP4 and the browser closes.
  6. Queue processing — a background job is created (the API returns immediately; the UI polls progress).
  7. Audio extraction — FFmpeg converts the MP4 to a 16 kHz mono WAV.
  8. Transcription — faster-whisper turns speech into transcript.txt locally.
  9. AI analysis — the AI Service Manager sends the transcript to Llama 3 (or Gemini if needed); the JSON reply is validated and normalised.
  10. Save results — summary/decisions/action items stored in MongoDB, Markdown notes on disk, action items become Tasks.
  11. RAG ingestion — notes + transcript are chunked, embedded with embeddinggemma and stored in the vector store.
  12. Notify — Notion page (optional) and summary email; the dashboard timeline shows every step.

6. Deep Dive: How the Bot Joins a Meeting

  • Signed-in profile: you sign in to Google once in a normal Chrome window (Settings → Connect browser session). Google stores a login cookie in browser-profile/; MeetAI never sees the password. Later joins reuse that session.
  • Waiting for Meet to load: Meet is a heavy single-page app — the Join button appears seconds after the page loads, so the bot polls for up to 60 s instead of checking once.
  • Guest screen: if not signed in, Meet asks “What’s your name?” and keeps Join disabled until a name is typed — the bot types the configured name and waits for the button to enable.
  • Mic and camera are OFF by design: the browser is launched with no camera/mic permission (--deny-permission-prompts), so the bot can never be heard or seen.
  • Waiting room: after “Ask to join” it waits up to 15 minutes for the host; recording starts only after admission.
  • Retries: refused or failed attempts retry every 30 s (10 attempts); each attempt appears on the Activity timeline, with a screenshot saved to logs/ for diagnosis.
How to say it: “The hardest part was making browser automation robust against a real, changing UI: waiting for elements properly, handling guest and waiting-room states, and making failures diagnosable with screenshots instead of silent errors.”

7. Deep Dive: Recording and Transcription

  • Playwright only drives the browser; FFmpeg is a separate process that records the desktop (gdigrab) and one audio device (dshow) to H.264 + AAC.
  • Before recording it verifies the audio device exists (FFmpeg 9 lists devices but exits with code 0 — a bug I had to fix).
  • Stopping sends q to FFmpeg so the MP4 is finalised properly (falls back to kill after 15 s).
  • Transcription auto-detects faster-whisper → openai-whisper → whisper.cpp, falls back from GPU to CPU, and keeps the MP4 even if transcription fails.
  • To capture other people’s voices on Windows you need a loopback device (Stereo Mix or VB-Audio Cable); a microphone only hears the room.

8. Deep Dive: AI Service Manager (Local First, Cloud Fallback)

FailureDetected byWhat the manager does
Ollama not runningconnection refusedmove to Gemini key 1 (15 s cooldown on Ollama)
Timeout / 5xxAbortController / statusretry once on the same provider
Rate limit (429)HTTP 429cool that key down (Google's retry hint or 60 s) → next key
Quota exhausted429 + 'quota'cool down 1 hour → next key
Invalid key400 'API key not valid' / 403disable that key permanently — never retried
Everything failed—clean 503 AI_PROVIDER_UNAVAILABLE error
  • Modes: auto (Ollama first), ollama (100% offline), gemini (cloud first).
  • Reliable JSON from a small model: strict prompt + format:"json" → extract JSON from the reply → validate with Joi → normalise (e.g. empty priority becomes MEDIUM) → one repair prompt if invalid.
  • Long meetings: transcripts over 12,000 characters are summarised in parts (map) and then merged (reduce), so nothing is silently cut by the 8k context window.
  • Security: API keys live only in the backend .env, go only in an HTTP header, and are redacted from logs.
How to say it: “I used a chain-of-responsibility style manager with error classification, so a 429 cools a key down, an invalid key is blacklisted, and the user only sees an error if every provider fails.”

9. Deep Dive: RAG — Asking Questions About Past Meetings

  1. Ingest: after each meeting, the AI notes and transcript are split into ~1,200-character chunks with 200-character overlap (cut at sentence/word boundaries).
  2. Embed: each chunk becomes a 768-number vector using embeddinggemma through Ollama (local).
  3. Store: vectors go to ChromaDB if configured, otherwise to MongoDB — every chunk is tagged with its owner and meeting.
  4. Query: the question is embedded with the same model; the 5 most similar chunks (cosine similarity) are retrieved.
  5. Answer: Llama 3 answers only from those chunks and cites them as [1], [2]… Private context is never sent to the cloud unless explicitly allowed.

Example from a real test: “What tasks were assigned in the Project Phoenix meeting?” → “Rahul: create the database schema by October 15th; Anita: benchmark faster-whisper by Friday; Priya: write the project report draft by October 20th [2]”.

10. Email, Activity Tracking and Logging

  • Email: Nodemailer over Gmail SMTP with an App Password. After analysis the summary (key points, decisions, action items, questions) is emailed to EMAIL_TO. Every attempt is stored in EmailLog as SENT / FAILED / SKIPPED; without SMTP the app keeps working.
  • Activity timeline: every stage writes a row (PENDING / RUNNING / COMPLETED / FAILED / RETRYING / SKIPPED) — shown on the dashboard and in each meeting’s Activity tab.
  • Logs: Winston writes meetai.log, error.log, ai.log (provider choice, fallbacks) and meeting.log (pipeline). Passwords, tokens and keys are redacted automatically.

11. Data Model and Storage

  • MongoDB stores metadata only — paths to files, never the MP4 itself.
  • Disk layout: recordings/<id>/meeting-<time>.mp4, transcripts/<id>/transcript.txt, meeting-notes/<id>/summary.md, browser-profile/, logs/.
  • Data isolation: every document has an owner; every query filters by it.
  • Soft delete for meetings and tasks; deleting a meeting also removes its search vectors.

16. Likely Interview Questions — With Answers

QuestionAnswer
Why local AI instead of OpenAI?Zero cost, privacy (meeting audio is sensitive) and works offline. Gemini is only a fallback.
How do you get reliable JSON from a small LLM?JSON mode, a strict schema in the prompt, extraction from the reply, Joi validation, normalisation, and one repair retry.
What is RAG and why use it?Retrieve the most relevant chunks with embeddings, then let the LLM answer only from them — accurate, citable answers without fine-tuning.
Why MongoDB?AI output is nested and evolves (key points, action items…); documents fit naturally. It also doubles as a vector store fallback.
How do long tasks not block the API?The API returns 202 and a job id; a background queue runs one job at a time; the UI polls status.
How do you handle failures?Each stage is isolated, transient errors retry, optional stages never fail a meeting, and earlier files are never deleted.
How do you keep API keys safe?Backend .env only, header-only transport, log redaction, never in the React bundle.
How does the bot know the meeting ended?It polls every 20 s for Meet’s end screens and the Leave button, with a grace period and two consecutive misses to avoid false stops.
How did you test browser automation without real meetings?A local mock that behaves like Meet (slow render, guest screen, waiting room, refusals) plus a real recording test.
What would you improve next?Speaker diarisation, a persistent job queue, Teams/Zoom adapters and a packaged desktop installer.

17. Demo Script (5 minutes)

  1. Dashboard — show the status strip (MongoDB, Ollama, Whisper, FFmpeg, RAG, Email all green) and explain local-first.
  2. Add meeting — paste a Meet link and time; explain the scheduler joins 2 minutes early.
  3. Join & record — Chrome opens and joins; open the Activity tab to show live stages and retries.
  4. Stop & save — processing runs in the background; show the transcript and AI summary tabs.
  5. Tasks — action items became tasks with owners.
  6. Ask meetings — ask “What decisions were made?” and show the cited answer.
  7. Email — show the summary email in the inbox.
  8. Settings — explain AI modes (auto / local only / Gemini) and the join name.
